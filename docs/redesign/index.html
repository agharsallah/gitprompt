Design proposal · dashboard restructure

One story, told at four zoom levels

Overview, Projects, Sessions and Prompts already hold everything needed to tell how your work with coding agents went. This proposal keeps every feature they have and reorganises them so each page reads as a story: a headline, one signature picture, chapters, then the evidence.

14 Nov 2026 Status: proposal, nothing built yet Based on the running app with real data and the code in web/src and backend/crates

01Where we are

I ran the daemon against the real local database and went through every page: Overview, Prompts with a selected turn, Sessions, a session story, Projects and a project story.

$453spent in 7 days; subagents took 43%
16 + 18Overview panels, and "Phase 1…18" in one project

The data is rich and accurate. The pages show it as inventories: long vertical lists where everything has the same weight. You can find any fact, but you have to build the story yourself.

Overview 16 panels, no headline

Each panel asks a good question, but the page doesn't say what happened this week, what changed since last week, or what deserves a look. It is 3,600px tall.

Projects Rows of numbers

Each project shows counts and a sparkline, but not where the work stands: which chapter it is in, whether it's active, or what was achieved.

Project story Phases without names

"Phase 1 … Phase 18", a table, then a 4,000px list with commit dumps (15 rows under one prompt). The shape of the project is lost.

Sessions Tall cards

About 150px each, so 5 per screen. The title is the first prompt, truncated. The turn sparkline, the most telling part, is the smallest. Parallel sessions are invisible.

Session story Turns with no arc

Turns are listed with facts, but there is no picture of how the conversation went: where it slowed down, where you reworded, where the money went. System items break up the reading.

Prompts Filters before content

Six rows of filters come before the first prompt. The reader is empty until you select something, then shows one long column with 7 tabs that mixes reading, annotating and debugging.

02The idea: one story, four zoom levels

Overview, Project, Session and Prompt are the same story seen from different distances. The navigation becomes a zoom: each page says where you are, lets you go one level in or out, and uses the same pictures for the same things.

03A visual vocabulary

Storytelling needs recurring characters. These glyphs mean the same thing on every page, so a turn seen in a project chapter is recognisable in its session and in the Prompts list. Each becomes a component in lib/ui/story/, shown on the Design system page.

05Page by page

For each page: the story it tells, a sketch, why each change helps, and what is kept. Labels come from your real data so the sketches feel concrete. Figures in the sketches illustrate the layout and are not measurements.

Overview

How did my week with the agents go, how does it compare, and what is worth a look?

A1 · The first screen

/?range=7d
  • A headline sentence in place of "Overview". It is built from the same totals the page already loads, plus the previous period for comparison. The filters fold into one "Filters · 2" button; the origin chips stay visible because they change every number.
  • The five key figures stay, each with a comparison and a link ("4 failed · see them" opens Prompts filtered on failed). A number without a baseline doesn't tell a story.
  • The week strip is the signature picture. It merges "prompts each day" and "spend per day" and splits each day by project, so you see where the effort went. It adds annotations (busiest day, a tag, an expensive day). Clicking a day opens that day's sessions on a timeline.
  • Worth a look ranks up to four items from data the panels already compute: failed turns, cost outliers, repeated prompts, possible secrets. Each opens the matching prompts. With nothing remarkable it says so in one line.
  • The four existing sections become tabs (plus Starred). Each tab opens with one takeaway sentence, then the existing panels, unchanged. The page goes from 3,600px to two screens, and every panel is still one click away.

Kept: range, origin chips, tool / app / project / model filters (in the Filters menu), Export, the setup steps when nothing is connected, the empty state, all 16 panels with their charts, toggles and "not available for …" notes, every bar and cell linking to prompts, live refresh when capture goes quiet.

Projects

Where is each piece of work, which ones are moving, and where did the effort and money go?

B1 · Projects as a portfolio of journeys

/projects?range=7d
  • The headline says where effort went and what moved (projects that entered a new chapter during the range).
  • A river with chapter names replaces the sparkline. Same data (prompts per day), but cut at the phase boundaries the backend already computes, so each row shows where the work stands and its current chapter.
  • The fingerprint of the last session shows how things are going right now: smooth (all teal), or struggling (red and amber).
  • Quiet projects fold away. Today a worktree folder and a scratchpad get the same space as your main project. They stay one click away, and they are counted.

Kept: range, one row per repository or folder, name and path, prompts with their share, sessions (linking to Sessions filtered), files written, cost, last prompt, prompts per day (now the river), the tool-kind bar (on hover and in the project story), branches, failed-turn badge, the link to the project story.

Project story

How did this project get from its first prompt to where it is now, chapter by chapter?

B2 · The journey

/projects/[id]
  • A narrative headline: from the first prompt to the latest, the commit count, the most expensive chapter. Every number in it is a link.
  • Milestones from git (tags, merges into the default branch, files under docs/adr/) anchor the timeline to moments people remember.
  • The river replaces the two "per phase" bar charts. Its width is prompts per day, and chapter dividers sit where phases start. 18 phases become 6 chapters: phases next to each other with similar words and the same branch merge, and the phase table stays inside each chapter.
  • Branch lanes and spend per day on the same time axis. Failed turns show as red dots on their branch, so "the strict-lints branch was rough" is visible without reading.
  • Chapter cards answer: what, how it went, what came of it. Each card has the outcome mix, rework, commits and cost. A chapter's name comes from its most frequent words and commit subjects, and you can rename it. Clicking a card opens the chapter (B3).

B3 · Inside a chapter

/projects/[id]#chapter-3
  • Goal, then how it went in plain sentences, then the existing phase table scoped to the chapter. The sentences are built from counts (finished, reworded, interrupted), never invented.
  • Prompts grouped by session, each session with its fingerprint. Rewording shows as an arc between the two prompts (lineage already finds them). Commit lists fold into one line ("30 commits +7,729 −851 ▸"), so 15-row dumps no longer interrupt the reading.
  • What came of it: commits, lines, the directories that changed most, the cost. This is the "advancement" the project page lacks today.

Kept: back link, name, path, date range, Export, the figures (prompts typed, sessions, phases, commits with lines and files, cost), "not shown: N prompts sent by the tool", prompts and cost per phase (now the river and the cards), the phase table, each phase's pause, date, branch, figures and outcome mix, every prompt entry with outcome, facts and "in its session", every commit with hash, subject, time and lines, anchors from Search results.

Sessions

Which conversations did I have, when, in parallel or one after another, and which went badly?

C1 · A day of sessions, then the list

/sessions?range=7d&day=2026-11-13
  • The headline names the pattern: how many sessions, how much in parallel, the longest one. Search, sort and the project filter stay; the project chips become one filter token.
  • The day timeline is the signature picture. One lane per session over the hours, coloured by project, with a tick per turn and red for failures. Parallel work, which you do a lot (3 sessions at once on Thursday), is invisible today. Clicking a day on the Overview opens here.
  • Compact rows with a fingerprint replace the tall cards. All the card's figures stay on one line; the fingerprint is bigger, not smaller. The title is a short label from the first prompt, which you can rename.
  • Grouped by day, like Prompts already is, so the list reads like a diary. Sorting by "Most turns" or "Costliest" switches to a flat list.

Kept: range, search what was asked, sort (recent, most turns, costliest), filter by project, "showing N of M" and loading more, title, project, branch, time span, permission mode, failed-turns badge, turns, span, tool calls, files changed, cost, the turn bars (now the fingerprint), models, "Every turn" (on hover or expand), Read the story, Open in prompts.

Session story

How did this conversation unfold, where did it get stuck, and what did it produce?

C2 · The conversation as an arc, then the turns

/sessions/[id]
  • A title and a headline. The session gets a name from its first typed prompt (you can rename it), and the headline sums up the arc: start, the hard part, the end, what changed.
  • The arc chart is the session at a glance. One bar per turn (height = time the agent worked, colour = outcome), cumulative cost, rewording arcs, commits and system markers on one axis. Clicking a bar scrolls to that turn. It stays pinned in small at the top while you scroll.
  • Each turn reads Ask → Work → Answer → Result, the same order as the prompt reader. "What the agent did" is a one-line replay with a plain summary, so a 30-minute turn is understandable without opening it.
  • System items become margin notes next to the turn they belong to: task notifications, subagent briefs, agent messages, compactions. Today they sit between turns and break the reading; now they are next to it.

Kept: back link (now the zoom bar), title, tool, app, model, project, branch, time range, Export, the figures (prompts typed, system items, span, tool calls, cost, commits after your prompts), the outcome bar (now the arc), each turn's number, time, outcome, branch, text, facts and tool mix, files written, commits, every marker group (subagents, agent messages, task notifications, compactions, briefs), reword markers, "Read it all in the prompt".

Prompts

What exactly did I ask, how did each turn go, and can I find it again?

D1 · List and reader together

/prompts?outcome=failed&id=1033
  • A headline and one query bar. Range, text, tag, tool, app, model, outcome and project become tokens in one field, with suggestions as you type. Origins and the quick filters (starred, failed, changed files, ran commands, possible secret) stay as chips with their counts. Six rows of filters become two.
  • A denser list, still grouped by day with the session line. Each row is two lines; connector, app, branch, tags and model show on hover and in the reader. About twice as many prompts fit on a screen.
  • Your notes come first: star, rate, copy, tags and note sit in the header, not between the answer and the tabs.
  • The turn told in five steps: You asked (with injected context folded, the secret warning, words and tokens) → What the agent did (a replay strip with a plain summary) → Claude answered (with the error, if any) → What came of it (files, lines, commits, cost) → Where it sits (its place in the session, versions, similar prompts that worked).
  • The 7 tabs stay, under "Details": Activity, Usage, Repository, Session, Versions, Events, Raw. Story first, raw evidence after. With nothing selected, the reader shows a summary of the current filter (outcomes, cost, the most expensive turn) instead of an empty card.

Kept: every filter (range, text, tag, tool, app, model, outcome, project, origins, quick filters with counts), Export, "newest N of M" and paging, grouping by day with the session line, live updates, row facts. In the reader: outcome, time, turn link, connector, project, branch, permission mode, version, star, worked well / didn't work, copy, close, your prompt with injected context, "show the whole prompt", agent and task voices, secret warning and redaction, worked for / tool calls / files, the turn timeline, the error callout, the answer, tags and notes, all 7 tabs. The /search page's word search with snippets lives here and in ⌘K.

Prompt reader, up close: Replay and Versions

Why did this turn take 30 minutes, and did a better-worded version do better?

D2 · Replay and the life of a prompt

reader › Replay · Versions
  • Replay draws the turn's events (already stored and listed under Events) as lanes over time: you, model calls, each tool kind, subagents, errors, commits. The question "why did it take 30 minutes?" gets a visual answer: two failed test runs and a long subagent.
  • Versions as a thread: each attempt with its outcome glyph and word changes, ending with "Outcome improved" when it did. This is how a person learns what wording works for them, using the existing lineage and word diff.

09Ready for teams: groundwork now, features in step two

Sharing with a team is the second step and only if people want it. What has to happen now is small: every record knows who made it, on which machine, in which workspace, and who may see it. With that in place, team features need no migration of anyone's history.

T1 · What the data model gains now

store + wire types

T2 · The same pages, in step two

workspace: platform-team
  • The story pages gain a "who" dimension without changing shape: the river splits into lanes per person, chapters and milestones stay shared. That works because the pictures are built from one query, and "who" is one more filter.
  • Rows get an avatar and a visibility state (yours, private, published). The "who:" token joins the query bar.
  • Publishing reuses the export pipeline (redaction, relative paths, figures-only defaults) behind a review that shows exactly what leaves, the same trust pattern as Connect's diff. Notes and raw events never leave.

Step two needs a team server (the daemon in team mode on a Postgres the team runs; PLAN.md already plans optional Postgres) and probably a new crate for sync. By the project's rules that is a design decision for you, so it is listed under Decisions, not assumed.

12Decisions for you

These change direction or touch guarded files, so they are yours. Each has my recommendation.

  1. Chapters: group phases or keep 18?Grouping makes long projects readable; the phase table stays inside each chapter.Recommendation: group, with names you can edit, and keep phases one level down.
  2. Where does the team server live (step two)?Self-hosted only, or also a hosted service?Recommendation: self-hosted first. A hosted service would break the "stays on this machine" promise, which is the product's strongest point.
  3. A new crate for sync (step two).It changes rules.rs and docs/extending.md.Recommendation: decide when step two starts. Steps 1–6 need no new crate.
  4. Navigation order.Far to near (Overview, Projects, Sessions, Prompts) or the current order?Recommendation: far to near, so the sidebar matches the zoom bar.
