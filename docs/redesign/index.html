Design proposal v3 · product review applied

A tool you use, not a report you read

Version 2 reorganised Overview, Projects, Sessions and Prompts into one story at four zoom levels. The design is good. The bet was wrong: it made the history nicer to read, and people rarely come back to read. Version 3 keeps the sketches and puts four reasons to open the app first: find a prompt again, pick a session up, see which prompt produced a commit, and see what the agents cost you.

14 Nov 2026 Status: proposal v3, nothing built yet v2 sketches unchanged unless marked v3

Interactive. Switch the states and tabs above each sketch. Inside the sketches, click links (›), tabs and chart marks; hover charts for values; click a numbered mark to find its explanation.

00Why people come back

Four moments in a working day when GitPrompt hands you something you would otherwise have to rebuild. Each takes seconds and ends with you back at work. The design is judged on these four first.

v3 W1 · Four moments, and what you leave with

click a card to see its screen

Reading the story of a week, a project or a session is still here (§02–§06). It is what you do after one of these four brought you in, so it no longer decides what gets built first.

What v3 changes

Reordered Value first, vocabulary as needed

Find and resume ship first, then the commit trace, then the Overview's first screen with tray and notifications. The reading redesign follows. Glyphs are built with the first page that uses them, not as a step of their own (§11).

Added The history outside the dashboard

gitprompt find, why and resume in the terminal, "the prompts behind this branch" for a pull request, and a weekly recap notification (R1 above).

Changed Redone work is a headline figure

One of the five Overview figures becomes what the turns you had to redo cost: failed, interrupted or reworded, in money and agent time. It reverses a v2 choice, so it is decision D3.

Changed Chapters must pass a test first

The project river is only as good as its chapter names. Before building it, generate names for your three largest projects and count how many you would keep. Below 8 in 10, phases stay as they are, with dates (D6).

Deferred Team columns, Compare, pinning

Identity columns leave step 1: adding columns with defaults costs the same later, and data leaving the machine is still a permanent non-goal. Also parked until someone asks: the Compare lens, pinned panels, ghost bars, custom compare ranges, the setup panel (C3; the strip stays), window vibrancy.

Changed What "done" means

v2: every existing feature is reachable. v3: each step names the job it serves and how we will know it worked. Every feature stays reachable in this round, since tabs make that cheap, but that is a constraint and no longer the goal (D1, D2).

The data is rich and accurate. The pages show it as inventories: long vertical lists where everything has the same weight. You can find any fact, but you have to build the story yourself.

Overview 14 panels, no headline

Each panel asks a good question, but the page doesn't say what happened this week, what changed since last week, or what deserves a look. It is 3,600px tall.

Projects Rows of numbers

Each project shows counts and a sparkline, but not where the work stands: which chapter it is in, whether it's active, or what was achieved.

Project story Phases without names

"Phase 1 … Phase 18", a table, then a 4,000px list with commit dumps (15 rows under one prompt). The shape of the project is lost.

Sessions Tall cards

About 150px each, so 5 per screen. The title is the first prompt, truncated. The turn sparkline, the most telling part, is the smallest. Parallel sessions are invisible.

Session story Turns with no arc

Turns are listed with facts, but there is no picture of how the conversation went: where it slowed down, where you reworded, where the money went. System items break up the reading.

Prompts Filters before content

Six rows of filters come before the first prompt. The reader is empty until you select something, then shows one long column with 7 tabs that mixes reading, annotating and debugging.

03A visual vocabulary

Storytelling needs recurring characters. These glyphs mean the same thing on every page, so a turn seen in a project chapter is recognisable in its session and in the Prompts list. Each becomes a component in lib/ui/story/, shown on the Design system page.

v3 These are names for components and for this document. On screen the labels stay in the user's words: project, session, prompt, commit, cost, and "phase" or "chapter" for a stretch of a project. A chart is introduced by the question it answers ("How did it go, turn by turn?"), never by "arc", "river", "fingerprint" or "replay".

States every panel supports

Every panel, list and story handles these six states the same way, so a page never shows a blank card, a misleading zero or a jump while you read. Use the switchers above the sketches below to see them in context.

For each page: the story it tells, a sketch, why each change helps, and what is kept. Labels come from your real data so the sketches feel concrete. Figures in the sketches illustrate the layout and are not measurements.

Overview

When and how do I work with the agents, how long do they work for me, what did it produce, and where does the money go?

Why you open it: to see what needs you. Sessions to pick up, things worth a look, what the week cost. Jobs: pick it up, stay in control.

v3 A1 · The first screen: what needs you, then how the week went

/?range=7d
States

More ideas to make the Overview better

Project story

How did this project get from its first prompt to where it is now, and which prompts and commits made each step?

Why you open it: to find the prompt behind a commit, or everything asked for in a stretch of work. Job: explain the code.

Links look the same everywhere. Anything that opens another level is in the accent colour and ends with an arrow: Prompt › opens the turn, Session › its session story, Commits › the commits it produced. A commit hash opens the commit (on the remote too, when the repository has one). Hovering a link shows where it goes.

B2 · The journey, with Prompts, Sessions and Commits one tab away

/projects/[id]?tab=journey
Tabs and states
  • A narrative headline: from the first prompt to the latest, the commit count, the most expensive chapter. Every number in it is a link.
  • Tabs: Journey, Prompts, Sessions, Commits. Prompts is the full Prompts list scoped to this project (every filter and the reader work there). Sessions is the Sessions list scoped the same way. Commits lists every commit with the prompt that produced it (B4). You never leave the project to trace something.
  • The river (width = prompts per day) cut into chapters, with milestones from git that link to their commit. 18 phases become 6 chapters: neighbouring phases with similar words on the same branch merge, and the phase table stays inside each chapter.
  • Commits per day get their own lane next to branches and spend, so you see when work turned into code.
  • Every chapter card ends with three links: its prompts, its sessions, its commits. Each opens the matching tab, filtered to that chapter's dates.

B3 · Inside a chapter: every prompt, session and commit is a link

/projects/[id]#chapter-3
  • Goal, then how it went in plain sentences, then the existing phase table for the chapter. The goal links to its prompt. The header links to all of the chapter's prompts and commits.
  • Every prompt line carries its links: Prompt ›, Versions › when it was reworded, and its commits, which unfold in place with hashes linking to each commit. Sessions open with Session ›. No more guessing what is clickable.
  • Traced both ways: from a prompt to its commits, and from a commit back to the prompt behind it. The directories that changed most show what the chapter achieved.

B4 · The Commits tab: every commit with the prompt that produced it

/projects/[id]?tab=commits
  • All commits of the project, searchable by subject, file or hash, grouped by chapter, branch or day. Commits made by hand (no prompt before them in a session) appear too, marked as such, so the list is complete.
  • Each commit names the prompt behind it, with links to the prompt, its session and the remote. It uses the existing "commits after a prompt" link, read the other way round.

Kept: back link, name, path, date range, Export, the figures (prompts typed, sessions, phases, commits with lines and files, cost), "not shown: N prompts sent by the tool", prompts and cost per phase (now the river and the cards), the phase table, each phase's pause, date, branch, figures and outcome mix, every prompt entry with outcome, facts and "in its session", every commit with hash, subject, time and lines, anchors from search results.

Session story

How did this conversation unfold, with which models and settings, what did it produce, and how do I pick it up again?

Why you open it: to resume the session with its command, or to see where it went wrong before you do. Job: pick it up.

C2 · Resume it, see its setup, read its arc

/sessions/[id]
States
  • Pick the session up where it stopped. The original session id with a ready command for its tool, run from the session's folder (claude --resume <id> for Claude Code). Copy it, or in the desktop app open it in a terminal directly. Session rows in the list get the same Copy resume action.
  • The setup at a glance: tool and version, app, models with the turn where they changed, permission mode and its changes, effort when the tool reports it, branch and commit at the start and end, MCP servers. "All settings ›" opens the full panel (C3).

Prompt reader, up close: Replay and Versions

Why did this turn take 30 minutes, and did a better-worded version do better?

Why you open it: to copy the wording that worked, and to see what a turn produced. Jobs: find it again, explain the code.

D2 · Replay and the life of a prompt

reader › Replay · Versions
  • Replay draws the turn's events (already stored and listed under Events) as lanes over time: you, model calls, each tool kind, subagents, errors, commits. The question "why did it take 30 minutes?" gets a visual answer: two failed test runs and a long subagent.
  • Versions as a thread: each attempt with its outcome glyph and word changes, ending with "Outcome improved" when it did. This is how a person learns what wording works for them, using the existing lineage and word diff.

Order of work v3

Each step ships on its own, keeps every existing feature working, and names the job it serves (§00). Shared pieces from the component table (glyphs, the zoom bar, the link style) are built with the first step that needs them and shown on the Design system page then. The steps are cut into 59 tickets, with a gate inside each phase and a checkpoint after it, in Delivery tickets.

Step 1Find and resumeM

⌘K, copy a prompt, the resume command, the recall shortcut

⌘K over prompts, sessions, projects and commits, with finished prompts first; /search redirects to it. Copy on every prompt row. A resume: template in each connector spec, the copy action on session rows and stories, session names you can edit. gitprompt find and gitprompt resume in the CLI. On desktop, the recall shortcut. Sidebar reordered.

Done when every current route works or redirects, and each resume command is verified against its tool's documentation and hidden where a spec has none.

It worked if you copy a past prompt or a resume command on most working days.

Step 2Explain the codeM

Commit → prompt, in the app, the terminal and a pull request

The commit → prompt lookup in the store. The Commits tab of a project (B4) on today's project page, "What came of it" in the prompt reader, gitprompt why <commit>, and "the prompts behind this branch" as a Markdown export.

Done when any commit that followed a prompt leads to that prompt in one step, and a commit made by hand says so.

It worked if the Markdown block ends up in your pull requests, or why answers a question you would otherwise have searched for.

Step 3Stay in controlM

The Overview's first screen, the tray, notifications

A1 only: the headline when it has something to say, the five figures with redone work, Worth a look with an action on every item, possible leaks (L1), and the existing panels behind tabs (A2 without its new panels). Previous-period comparison in stats. On desktop: the live tray menu, notifications for a long turn, a possible secret and a quiet connector, the weekly recap.

Done when the Overview fits two screens and every Worth a look item and notification opens the turn it is about.

It worked if you act on a Worth a look item most weeks (a hidden value, a prompt turned into a command), and no notification kind gets switched off for being noisy.

Step 4Read a turn and a sessionL

Query bar, the reader as a story, the session arc

QueryBar and two-line rows in Prompts; the reader as Ask → Work → Answer → Result with Details tabs, Replay and the versions thread; compact session rows, the day timeline, the session arc with model changes and the setup strip.

Done when every filter and tab in the §08 checklist is reachable and saved links still work.

It worked if "why did this turn take so long?" is answered from the reader without opening Events or Raw.

Step 5Project journeysL

Chapters, the river, milestones: only after the naming test

First a spike in insights: chapter names from branch names and commit subjects, run on your three largest projects (D6). If the names hold: chapters, ProjectRiver, milestones from git, chapter cards, the Prompts and Sessions tabs. If they don't: phases keep their dates and get the same links and tabs, without the river.

Done when the spike result is recorded in an ADR and the page built matches it.

Prompts per hour, agent run lengths, the commits panel, the contribution calendar; gitprompt:// links and gitprompt open; remembered window size and ⌘1–⌘4. Measured with just perf.

LaterAI analysisM

Settings section, request preview, the labelled summary card on Overview, project and session. Off by default.

Identity columns and their ADR (moved here from step 1), publish review, signed bundles, a team server, the "who" dimension on every page.

12Decisions for you

These change direction or touch guarded files, so they are yours. Each has my recommendation.

  1. What "done" means. v3v2: every existing feature reachable. v3: each step serves one of the four jobs and says how we will know.Recommendation: v3. Keep every feature reachable in this round, as a constraint.
  2. Local usage counts. v3To learn which panels and actions are used, count opens and copies in your own database, show them under Settings › Developer, never send them. It is a new kind of stored data, so it is yours to allow.Recommendation: yes. Without it, "it worked if" stays a feeling and every later cut is a guess.
  3. Redone work as a headline figure. v3This reverses the v2 review choice to keep failures out of the headlines.Recommendation: yes, as cost and agent time, never as a count of failures.
  4. Open in Terminal. v3The desktop app would start your tool with the resume command. PLAN.md lists "automating any tool" as a permanent non-goal.Recommendation: ship Copy only. Add Open in Terminal only if you decide a click that runs one visible command is within the rule.
  5. Agents reading the history. v3gitprompt find and why are commands you run. An MCP server would let an agent query your history on its own, which is useful and close to the non-goal "adding context to prompts".Recommendation: the CLI now. No MCP server until you rule on it.
  6. Chapters: group phases, or keep 18?Grouping makes long projects readable only if the names are good. v3 Names come from branch names and commit subjects, which a person wrote, before typed words.Recommendation: run the naming test on three projects. Group if you would keep 8 names in 10 unedited; otherwise keep phases with dates.
  7. Team groundwork now, or with teams? v3Includes where a team server would live and the new crate for sync, which changes rules.rs and docs/extending.md.Recommendation: all of it with teams. Self-hosted first when that day comes; a hosted service would break "stays on this machine".
  8. Which AI providers, when AI analysis comes?A local model only, or also your own API key for a hosted model?Recommendation: both, off by default, figures only unless you also allow prompt text, and a preview before every request.
  9. Resume commands as connector data.A resume: template in each spec, verified per tool version.Recommendation: yes; hide the action for a tool without one.
  10. Navigation order.Far to near (Overview, Projects, Sessions, Prompts) or the current order?Recommendation: far to near, so the sidebar matches the zoom bar.
