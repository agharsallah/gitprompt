# 0016 — Prompt stories: phases, lineage by text similarity, search snippets, and the stories API

**Status:** accepted (implemented)
**Amends:** [0012](0012-prompt-index-and-stats.md) (search snippets, which §7 left for later), [0014](0014-insights-stats.md) (stories reuse the index, `OUTCOME` and the filters)

## Context
Plan epic E4 asks for ordered, explained views of what the user typed at three zoom levels (a session, a project, one prompt's versions) plus full-text search with snippets. Rules that bind it: a story never shows system-originated text as typed (ADR-0010); every element links to the prompt detail; a project with 200+ prompts renders without jank; similarity uses no embeddings and no heavy dependency; E5 will export stories to Markdown and self-contained HTML, so data and presentation stay apart.

## Decision
1. **Stories are built on read from the prompt index**, like statistics: `storage/timeline.py` reads index rows in time order with the typed text (`prompt_fts`) and `store.OUTCOME`, plus the few turn events a story shows (`PostToolUse` file paths and Agent tool briefs, `PreCompact`), extracted with `json_extract` so no payload is parsed in Python. `insights/stories.py` shapes them with pure functions. Nothing new is stored; no index column was added.
2. **API.** `GET /api/stories/session/{session}`, `GET /api/stories/project/{project}`, `GET /api/stories/prompt/{id}` (lineage) and `GET /api/search` (the prompt filters, `q`, `limit`). Response models are in `api/routes/stories.py`. A project id is the **base64url of its git root (or folder), unpadded**: stable, URL-safe and reversible, so neither the daemon nor the dashboard needs a lookup table (`stories.project_id`, `lib/stories/story.ts projectId`; a test checks both agree).
3. **Only typed text becomes story content.** Chapters (session) and entries (project) are prompts whose origin is `typed` or `slash_command`. Everything else is a **marker**: system-origin prompts, subagent briefs (the Agent tool's `tool_input.prompt`, written by the model) and compactions. Consecutive markers fold into one group between two chapters. Their text is shown quoted, muted and labelled by kind (icon and label), never in the "you" voice. A project story counts system prompts (`system`) without listing them; lineage of a system prompt is empty.
4. **Phases** (`stories.phases`): a new phase starts after a **pause of 3 hours or more** (measured from the end of the previous turn) or when the **branch changes and the new branch holds for 2 prompts** in a row (a single prompt sent from another branch is a detour, listed in the phase's branches). On the local data (225 typed prompts, 19 projects) the gaps between a project's consecutive prompts (start to start) split into minutes and many hours: 45 gaps ≥ 30 min, 23 ≥ 2 h, 19 ≥ 3 h, 17 ≥ 4 h, 14 ≥ 6 h out of 208; 3 h sits in that valley and gives the busiest projects 3–4 phases. Session boundaries are not used: parallel sessions interleave (many session changes are 0–6 minutes apart). `CwdChanged` is not used either: 687 events, mostly from shells and subagents, so it says nothing about the user's work. Compactions are markers, not boundaries.
5. **Commits** come from one `git log --branches --since --until --shortstat` per story (`core/git.history`), not one call per prompt (200 prompts would be 400 git calls). Each commit is attributed (`stories.attribute_commits`) to the latest prompt before it, unless a turn that ran `git commit` was still going (or had ended within 2 minutes): then to that turn, which keeps parallel sessions apart. The prompt detail keeps its exact `head..next_head` range; stories say "commits made after your prompts".
6. **Lineage by text similarity** (`insights/lineage.py`, standard library only). Text is normalized (lower case, punctuation as spaces, spacing collapsed, first 4,000 characters). Similarity is the **mean of character-trigram Jaccard and word Jaccard**; 0 when the normalized lengths differ by more than 2× (a short instruction and a long pasted brief share many trigrams by vocabulary alone). Two prompts are **versions from 0.5**. Measured on the 228 typed prompts of the local data: 151 pairs reach 0.5 (57 identical texts, 96 reworded: 8 in the same session, 71 across projects), and 71 prompts have at least one version. The distribution has a valley right below the threshold (9 pairs in 0.45–0.5, 34 in 0.5–0.55); pairs above read as one instruction reworded or extended, pairs below as short texts sharing a verb but asking for different things. Trigrams alone (tested first) scored unrelated long pasted texts at 0.44–0.51; the word half and the length guard removed them. A lineage compares one prompt with at most 5,000 typed prompts (newest first) and keeps the 19 closest; a session or project story also marks **retries**: a prompt that is a version of one of the 30 before it in its session.
7. **Word diff and outcome change.** Each version carries `diff`, runs of equal/delete/insert tokens from the version before (`difflib.SequenceMatcher` over word, space and punctuation tokens), and `change`: improved / worse / same by outcome rank (failed < superseded = open < done; running has no verdict). The dashboard renders the diff with `<del>`/`<ins>` and hidden "added/removed" labels.
8. **Search snippets** are computed in Python (`insights/snippets.highlight`): a window of 180 characters starting near the first match, on a word boundary, with every match of every searched word marked. Matching is the same as the `q` filter (substrings, any case, short words included), which FTS5's `snippet()` would not do for words under 3 characters. The API returns `[{text, hit}]` segments, so the page renders `<mark>` from data and never injects HTML.
9. **Rendering.** Story pages are dynamic routes in a static build: SvelteKit writes a `200.html` fallback and the daemon's `Dashboard` static files return it for page paths without a file (never for `/api`, `/ingest` or assets). Project phases render 40 prompts at a time ("Show more") and use `content-visibility: auto`. Measured on a synthetic project of 270 typed prompts (plus 54 task notifications, 72 commits): story API 60 ms, page rendered in about 290 ms, scrolling to the end 460 ms. The largest real project (53 typed prompts) renders in about 290 ms with a 75–160 ms API call; the largest real session (196 prompts, 12 typed) in about 300 ms.

## Consequences
+ The three stories and search reuse the index, the filters and `OUTCOME`; the only new SQL reads the turn events a story shows.
+ E5 can export the same JSON: `insights/stories.py` and `lineage.py` have no I/O, and `diffstatText`, `phaseReason`, `markerSummary` (`lib/stories/story.ts`) are pure.
− Commit attribution by time can be wrong when two sessions commit in the same repository at the same moment without a `git commit` from the agent.
− Lineage compares in Python per request: fine for thousands of prompts, but a history of 100k typed prompts only looks at the newest 5,000.
− Phase rules are constants, not preferences; changing them changes every project story (nothing to migrate).

## Alternatives considered
- **Local embeddings** for similarity: better at paraphrase, but a model download and a heavy dependency for prompts that are mostly short, reused instructions; the text measure separates them well on the real data.
- **MinHash/LSH:** only needed to avoid an all-pairs comparison; stories compare a bounded window, and a lineage one prompt against the rest.
- **Store phases or similarity in the index:** they depend on neighbouring prompts (a new prompt can change a phase or a version list), so they would need the same "derived at query time" treatment as `followed`; computing them per story is cheap.
- **Hash-based project ids:** shorter URLs, but a lookup table on both sides.
- **FTS5 `snippet()`:** cannot highlight words under 3 characters, and returns markup to inject.
