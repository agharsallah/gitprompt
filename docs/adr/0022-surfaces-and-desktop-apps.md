# 0022 — Surfaces: where a prompt was typed, and prompts from desktop apps

**Status:** accepted (implemented)
**Builds on:** [0008](0008-universal-capture-declarative-sources.md) (declarative sources), [0010](0010-prompt-origin.md) (origin rules), [0015](0015-connector-layers-and-states.md) (layers), [0017](0017-connector-capabilities.md) (capabilities), [0019](0019-codex-connector.md) (Codex), [0021](0021-turn-facts-and-field-coverage.md) (facts, field coverage)

## Context
Prompts are now typed in desktop apps too: the Code tab of Claude Desktop, the Codex desktop app and Cursor. The question was which of them GitPrompt can capture within its rules (documented interfaces only, never the apps' own storage), how to tell them apart, and whether they land in the right session and project. Research, re-checked 2026-11-07 (sources in [docs/sources.md](../sources.md#desktop-apps)):

- **Claude Desktop, Code tab.** It shares `~/.claude/settings.json`, and "hooks … apply to both" ([desktop](https://code.claude.com/docs/en/desktop), [hooks](https://code.claude.com/docs/en/hooks)), so the Claude Code connector already receives its prompts. Hook payloads don't say which client sent them. The telemetry does: `service.name` is `claude-code-desktop` for local Code tab sessions, and `app.entrypoint` names the client (`cli`, `sdk-cli`, `sdk-ts`, `sdk-py`, `claude-vscode`, `claude-in-slack`; Desktop's own `claude-desktop`, `claude-desktop-3p`) ([monitoring](https://code.claude.com/docs/en/monitoring-usage)). Unverified: whether Desktop exports telemetry configured in *user* settings (the desktop page names managed settings). Desktop sessions can run in git worktrees under `<project>/.claude/worktrees/`.
- **Claude Desktop chat** has no hook, telemetry or local API; the only export is the account data export by email. It can't be captured without reading the app's local storage, which GitPrompt never does.
- **Codex desktop app.** The CLI, IDE extension and app share `$CODEX_HOME` and its hooks ([hooks](https://learn.chatgpt.com/docs/hooks)), so the Codex connector already receives it. No hook field says which client sent it (`SessionStart.source` is startup/resume/clear/compact/fork); the client name exists only in app-server and OTel (`originator`), whose values aren't documented.
- **Cursor** documents command hooks in `~/.cursor/hooks.json` ([hooks](https://cursor.com/docs/hooks)) with `conversation_id`, `generation_id` (changes per user message), `model`, `cursor_version`, `workspace_roots`, `user_email` and `transcript_path` on every event. Permission hooks block on an answer that isn't valid JSON; `beforeSubmitPrompt` expects `{"continue": …}`; other failures fail open. Nothing tells the IDE from the Cursor CLI, whose prompt hooks forum reports say are unreliable.
- **Antigravity** has hooks but still no prompt-submit event (`lastUserInput` on every event), so no connector yet.

The worktree case was a bug: a prompt's project is its `git_root`, which was `git rev-parse --show-toplevel`, i.e. the worktree's own folder, so every Desktop or Claude Code worktree became its own project.

## Decision
1. **A surface dimension, separate from the connector.** A surface is the app or client a prompt was typed in (`cli`, `vscode`, `desktop`, `sdk`, `cursor`…). A spec declares ordered `surface` rules, `{when: <origin rule conditions>, surface: <id>}`: a path (with `equals`) of the prompt's payload, or of an event of its turn (`event: user_prompt`). `insights/surface.py` evaluates them on read, first match wins; **no match is `null`, never a guess**. Names and icons are data (`surfaces` in `_defaults.yaml`, a spec adds its own; the dashboard maps icon names in `lib/prompts/surface.ts`). The surface is in the facts contract (`facts.surface`), an index column, a filter (`surface`, a list), a `/api/stats` grouping (named by `detail`), part of the rules version, and in exports ("Claude Code (Desktop app)", a `surface` column).
2. **Claude Code's rules** read its telemetry `user_prompt` event: `service.name = claude-code-desktop` first, then each documented `app.entrypoint`; a payload with `cursor_version` (Cursor running Claude Code's hooks) is `cursor`. Without the telemetry layer the surface is unknown. Codex, Copilot CLI and Cursor have no rules: nothing in their payloads says which client sent them.
3. **What a connector can and can't capture** is spec data too: `captures` (surface → note) and `cannot_capture` (app → why), listed on each connector card ("Where your prompts come from"), so Claude Desktop chat is shown as not captured, with the reason, rather than silently missing.
4. **A Cursor connector** (`cursor.yaml`): the curl forwarder in `~/.cursor/hooks.json` on `sessionStart`, `beforeSubmitPrompt`, `postToolUse`, `postToolUseFailure`, `subagentStop`, `afterAgentResponse`, `stop`, `sessionEnd`, answering `{"continue":true}` to the prompt hook and `{}` to the others, always exit 0, never `failClosed`, no permission hook. Two generic spec features made it data, not code: `event_names` (the tool's event → GitPrompt's, optionally by a payload value: `stop` with `status: aborted` is an `Interrupt`, `error` a `StopFailure`), and `answer` (where a turn's final answer is: Cursor's `afterAgentResponse.text`; default `Stop.last_assistant_message`). `generation_id` is the prompt id, `conversation_id` the session, the first workspace root the folder (every root is kept in `workspace_roots`), `cursor_version` the tool version. A third, `discard`, removes payload keys before anything is stored: Cursor's `user_email` is never stored.
5. **Projects resolve to the main repository.** In a linked worktree, `git_root` is the main repository (from `--git-common-dir`), `git_worktree` is true and `git_worktree_root` keeps the worktree; commits after a prompt are read from the worktree (its own HEAD). Subfolders resolve to their repository, a folder without git is its own project.
6. **Checking it live.** `GET /api/sources/recent` and `gitprompt check` list the newest prompt of each connector and surface with its time, project, branch (worktree), session, model, count and the values the surface rules read (`signals`), so a user can type one prompt per app and see how it was attributed. The Connectors page shows the same as "Recent captures".

## Consequences
- A new client of an existing tool is one `surface` rule and maybe a `surfaces` entry; old prompts get it on the next read (the rules version rebuilds the index).
- Codex and Cursor prompts show their tool with no app; if the tools ever document a client field, a rule adds it.
- Prompts captured from worktrees before this change keep the worktree as their project (their context was observed at ingest; the worktree may no longer exist to ask git).
- Unverified, to confirm with live use: Desktop's telemetry from user settings and its exact `app.entrypoint`; that Cursor runs hook commands through a shell and accepts `{}` on non-permission events; Cursor's tool input names.
